# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 십자가(Cross)인지 X인지 판별하는 Python 콘솔 프로그램입니다.

## 1. 실행 방법

- 실행 환경: Python 3.8 이상(개발·테스트는 3.12.10), 외부 라이브러리 없음
- `main.py`와 `data.json`을 같은 폴더에 두고 아래 명령어로 실행합니다.

```
python main.py
```

- 실행하면 모드를 고르는 화면이 나옵니다.
  - `1` : 사용자 입력 모드. 3×3 필터 A, B와 패턴을 한 줄씩 공백으로 구분해 입력합니다.
  - `2` : data.json 분석 모드. 5×5, 13×13, 25×25 케이스를 한꺼번에 판정합니다.
- data.json 위치: `main.py`와 같은 폴더입니다. 프로그램은 실행 위치와 상관없이 스크립트가 있는 폴더 기준으로 이 파일을 찾습니다.

## 2. 구현 요약

### 라벨 정규화
- 프로그램 안에서는 표준 라벨 `Cross`, `X` 두 가지만 씁니다.
- `LABEL_MAP`으로 여러 표기를 표준 라벨로 바꿉니다. 대소문자와 앞뒤 공백은 무시합니다.
  - expected 값: `'+'` → `Cross`, `'x'` → `X`
  - filter 키: `'cross'` → `Cross`, `'x'` → `X`
- 같은 뜻인데 표기가 다르면(예: `'+'`와 `'cross'`) 비교 결과가 틀어집니다. 그래서 비교하기 전에 반드시 정규화합니다.

### MAC 연산
- `mac(pattern, filt)` 함수는 이중 `for` 반복문으로 같은 위치의 값끼리 곱하고, 그 결과를 `total`에 계속 더합니다.
- NumPy 같은 외부 라이브러리는 쓰지 않았습니다.

### MAC 점수의 의미와 해석
- **MAC 점수가 클수록 입력 패턴이 그 필터와 더 비슷하다(유사도가 높다)는 뜻입니다.**
- 패턴에서 값이 있는 칸과 필터에서 값이 있는 칸이 많이 겹칠수록 곱한 값이 많이 남습니다. 그래서 점수가 올라갑니다. 반대로 겹치는 칸이 적으면 곱셈 결과가 대부분 0이 되어 점수가 낮아집니다.
- 해석 예시 (3×3, 0/1 값):
  - 십자가 패턴 × 십자가 필터: 5칸이 모두 겹쳐서 점수는 **5** → 매우 비슷함
  - 십자가 패턴 × X 필터: 가운데 1칸만 겹쳐서 점수는 **1** → 거의 다름
  - 따라서 이 패턴은 점수가 더 큰 **Cross**로 판정합니다.
- 주의할 점: 점수는 **같은 입력에 대해 두 필터의 점수를 비교할 때** 의미가 있습니다. 필터마다 가중치가 다르기 때문에(예: size_13 X 필터의 가운데 값은 7.5) 점수의 절대값만 보고 판단하면 안 됩니다.
- 두 점수의 차이가 1e-9보다 작으면 어느 쪽이 더 비슷한지 말할 수 없으므로 UNDECIDED로 처리합니다.

### 동점 처리 정책(epsilon)
- `abs(score_a - score_b) < 1e-9`이면 동점으로 보고 `UNDECIDED`(모드 1에서는 "판정 불가")로 처리합니다.
- 동점이 아니면 점수가 더 큰 쪽으로 판정합니다.

### 입력 검증과 예외 처리
- 모드 1: 3줄을 모두 입력받은 뒤 검사합니다. 열 개수가 다르거나 숫자가 아닌 값이 있으면 안내 문구를 출력하고 다시 입력받습니다.
- 모드 2: 키 형식(`size_N_idx`), 필터 존재 여부, 패턴과 필터의 N×N 크기, expected 값을 케이스마다 검사합니다. 문제가 있으면 그 케이스만 FAIL로 처리하고 사유를 남깁니다. 프로그램은 중간에 멈추지 않습니다.

### 새 라벨 추가 절차 (예: 원 모양 `Circle` 추가)

지금 코드는 Cross와 X 두 라벨만 비교하도록 만들어져 있습니다. 새 라벨을 추가하려면 아래 순서대로 진행합니다.

**1단계: 라벨 정규화 확장**
- `LABEL_MAP`에 새 표기를 추가합니다. `normalize_label()`은 이 표만 보고 라벨을 바꾸기 때문에, 함수 자체는 고치지 않아도 됩니다.
  ```python
  LABEL_MAP = {
      "+": "Cross", "cross": "Cross",
      "x": "X",
      "o": "Circle", "circle": "Circle",   # 추가
  }
  ```
- 같은 라벨을 가리키는 표기가 여러 개라면 모두 등록합니다. 대소문자와 앞뒤 공백은 이미 함수에서 처리합니다.

**2단계: 판정 흐름 수정**
- `load_filters()`: 지금은 Cross와 X가 모두 있어야 필터를 로드합니다. 이 조건을 "`LABEL_MAP`에 있는 표준 라벨이 모두 있어야 함"으로 바꿉니다.
- `analyze_case()`와 `decide()`: 지금은 점수 2개만 비교합니다. 라벨마다 `mac()` 점수를 구해 **가장 큰 점수의 라벨**을 고르도록 바꿉니다.
- 동점 규칙은 그대로 둡니다. 1등과 2등의 점수 차이가 1e-9보다 작으면 UNDECIDED로 처리합니다.

**3단계: 데이터 추가**
- data.json의 각 `size_N` 필터에 `"circle": [[...]]`를 추가합니다.
- `patterns`에 원 모양 입력과 `"expected": "o"`가 들어간 케이스를 추가합니다. 키 이름은 `size_{N}_{idx}` 규칙을 따릅니다.

**4단계: 테스트 절차**
1. `python main.py` → 모드 2를 실행해 필터 로드 화면에서 새 라벨이 함께 로드되는지 확인합니다.
2. 새로 추가한 원 패턴 케이스가 `판정: Circle | expected: Circle | PASS`로 나오는지 확인합니다.
3. 기존 6개 케이스의 결과(3 PASS / 3 FAIL)가 바뀌지 않았는지 확인합니다. 새 필터 때문에 기존 판정이 흔들리면 안 됩니다.
4. 일부러 등록하지 않은 라벨(예: `"expected": "triangle"`)을 넣어보고, 프로그램이 멈추지 않고 `알 수 없는 expected 값` 사유로 해당 케이스만 FAIL 처리되는지 확인합니다.

### 성능 측정
- `time.perf_counter()`로 `mac()`을 호출하는 구간만 10회 반복해 측정하고 평균을 냅니다. 입력·출력·파일 읽기 시간은 빠집니다.

## 3. 결과 리포트

### 3-1. 실행 결과 요약 (data.json)

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

총 6개 중 통과 3개, 실패 3개입니다.

### 3-2. FAIL 원인 분석

실패 원인은 "데이터/스키마 문제", "로직 문제", "수치 비교 문제" 세 가지로 나눠서 점검했습니다.

1. **데이터/스키마 문제가 아닙니다.** expected 값 `'+'`, `'x'`와 필터 키 `'cross'`, `'x'`가 모두 정상적으로 정규화되었습니다. 키에서 N을 뽑는 과정이나 크기 검증에서 걸린 케이스도 없습니다.
2. **MAC 로직 문제도 아닙니다.** 모드 1에서 문제 예시와 같은 점수(A 1.0, B 5.0)가 나왔고, 나머지 3개 케이스도 정상적으로 PASS했습니다.
3. **실제 원인은 수치 비교, 즉 "수학적으로 같은 점수"입니다.** 실패한 3개 케이스는 필터 가중치 때문에 두 점수가 수학적으로 정확히 같아지도록 만들어져 있습니다.
   - size_5_1: Cross 필터의 가운데 값 0.9 × 1 = **0.9**, X 필터 0.1 × 9칸 = **0.9**
   - size_13_2: Cross 필터 0.3 × 25칸 = **7.5**, X 필터의 가운데 값 = **7.5**
   - size_25_1: Cross 필터의 가운데 값 = **4.9**, X 필터 0.1 × 49칸 = **4.9**
4. 컴퓨터는 0.1, 0.3 같은 소수를 2진수로 정확히 나타내지 못합니다. 그래서 여러 번 더하면 아주 작은 오차가 쌓입니다(**부동소수점 오차**). 예를 들어 0.1을 9번 더하면 0.9가 아니라 0.8999999999999999가 됩니다.
5. epsilon 없이 `>`로만 비교했다면 이 아주 작은 오차가 승패를 정했을 겁니다. 그러면 size_5_1은 Cross, size_13_2는 X, size_25_1은 Cross로 판정되어 **세 케이스 모두 expected와 반대인 오답**이 나옵니다.
6. epsilon 정책을 쓰면 차이가 1e-9보다 작을 때 "판정 불가"로 처리합니다. 오차 때문에 생긴 우연한 오답을 내는 대신 "구별할 수 없음"을 그대로 보고하는 것입니다. 결과는 여전히 FAIL이지만, 이것은 **동점 규칙에 따른 의도된 FAIL**입니다.
7. 결론적으로 이 3개 FAIL은 데이터 설계상 필터가 두 패턴을 구별하지 못하는 경우입니다. 해결하려면 코드가 아니라 필터 가중치를 고쳐야 합니다. 예를 들어 X 필터의 대각선 가중치를 Cross 필터보다 충분히 크게 바꾸면 됩니다.

### 3-3. 성능 분석 (평균/10회, 실측)

| 크기(N×N) | 평균 시간(ms) | 연산 횟수(N²) | 1회당 시간(ms) |
|---|---|---|---|
| 3×3 | 0.0015 | 9 | 0.000167 |
| 5×5 | 0.0027 | 25 | 0.000108 |
| 13×13 | 0.0134 | 169 | 0.000079 |
| 25×25 | 0.0520 | 625 | 0.000083 |

### 3-4. 시간 복잡도 O(N²) 근거

1. MAC 연산은 N×N 배열의 모든 칸을 한 번씩 방문해 곱셈 1번과 덧셈 1번을 합니다. 그래서 연산 횟수는 정확히 **N²**입니다.
2. 반복문 구조로 보면 바깥 `for`가 N번, 안쪽 `for`가 N번 돌아서 N × N = N²번 실행됩니다. 따라서 시간 복잡도는 **O(N²)**입니다.
3. N이 2배가 되면 연산 횟수는 4배가 됩니다. 13 → 25는 약 1.9배이므로 연산 횟수는 169 → 625로 **약 3.7배** 늘어납니다.
4. 실측 시간도 0.0134 → 0.0520ms로 **약 3.9배** 늘어서, 연산 횟수가 늘어난 비율과 거의 같습니다.
5. 13×13과 25×25에서 "1회당 시간"은 0.00008ms 정도로 거의 일정합니다. 즉 시간은 N²에 비례합니다.
6. 3×3, 5×5는 1회당 시간이 더 크게 나왔습니다. 연산량이 워낙 적어서 함수 호출이나 반복문 준비 같은 고정 비용의 비중이 커지기 때문입니다. 크기가 커질수록 이 고정 비용은 무시할 수 있을 만큼 작아집니다.
7. 실제 AI 모델은 이런 필터를 수천 개, 이미지의 수많은 위치에 적용합니다. 그래서 MAC 횟수가 수억 번에 이릅니다. CPU처럼 하나씩 순서대로 계산하면 N²에 비례해 느려지므로, 여러 MAC을 동시에 처리하는 NPU가 필요합니다.
8. 측정값은 컴퓨터 상태에 따라 조금씩 달라질 수 있습니다. 그래서 10회 평균을 사용했고, I/O를 제외한 연산 구간만 측정했습니다.
